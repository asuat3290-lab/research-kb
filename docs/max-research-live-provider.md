# MR-2B1A Pre-live Provider Boundary

MR-2B1A is the historical pre-live offline/control-plane phase. Max schema 8 and 9 are
historical phases. MR-2B1 added independent Max control
schema 9 through `009_mr2b1_live_network_authorization.sql`; this phase adds
schema 10 through `010_mr2b1a_live_dispatch_permit.sql`. Core research schema
5 and Max migrations 001-010 remain separate and byte-for-byte frozen.
Migration 007 is `007_mr2b0r_authority_budget_closure.sql`.
The migration persists only hash-bound authority, policy, consumption, access
event, and attempt metadata. It never stores a credential, request/response
body, source text, PDF, passage, or absolute path.

## Authority chain

An administrator creates a `LiveNetworkAuthorization` only for a bound Run and
registered ProviderProfile. The record binds the Run, project, charter hash,
provider profile, model, endpoint-policy hashes, network-policy hash, pricing
and budget hashes, caps, validity window, reason hash, and server-owned actor.
The provider identity is stored and checked independently of the profile hash.
Use also requires the consumed StartApproval, the consumed LiveExecutionGrant,
and a live lease/fencing token. Consumption is one append-only row protected by
a unique authorization key and `BEGIN IMMEDIATE`; retries return the same
record and competing consumers cannot create a second row.

Each authorization has its own access-event SHA-256 chain. The database
rejects update/delete on authority, consumption, event, and attempt history.
`verify` recomputes the authorization hash, current projection, one-time
consumption, chain continuity, and binding facts. Backup and restore are
accepted only after the same verification succeeds.

## Physical-send permit

`LiveDispatchPermit` is generated by the control store, not accepted from a
client. Its immutable binding includes authorization and consumption IDs,
run/project, grant/profile/model/pricing/budget hashes, provider claim and
physical attempt, request/wire/intent/logical-call and idempotency hashes,
endpoint and network policy hashes, worker session/fencing token, and bounded
creation/expiry timestamps. Claim reservation, physical-attempt ownership,
budget reservation, authorization consumption, and permit creation are one
`BEGIN IMMEDIATE` transaction. A settled durable replay is returned before any
new authority consumption. A send-started crash is recorded as `unknown` and
cannot be retried automatically; a stale fencing token cannot write an
outcome.

## Credential and network boundary

The database stores only a normalized `CredentialRef` hash. The default live
transport factory returns `DisabledLiveTransport`, so import, readiness, CLI,
and read-only preflight cannot resolve a credential or open a socket. The
production-shaped permit factory can assemble only a registered, run-bound
profile with the named secure resolver, standard-library DNS resolver, and
standard-library HTTPS connector; it is not invoked by CLI or readiness in
this phase. Injected resolver/DNS/connector instances are fixture-only.

The separately injectable HTTPS transport checks the exact HTTPS origin and
path, rejects credentials/query/fragment/local or private addresses, validates
all DNS candidates before credential resolution, rejects caller-supplied
authorization headers and payload fields, and does not follow redirects. Any
expiry, replay, cross-run/project, provider/model, endpoint, DNS-rebinding, or
redirect-boundary mismatch fails closed before a provider dispatch.

The MR-2B1A test transport is hermetic and in-memory. No real API key, real
provider, network connection, model call, or charge is part of this phase.
`provider-live-smoke` accepts only run, authorization, exact hash and profile
confirmation plus a fixed request; `--execute` is refused. The first real
HTTPS call is a separate future approval requiring an explicit endpoint,
model, token/cost caps, credential source, and rollback plan.

## MR-2B2 extension (schema 11)

MR-2B2 adds an ordered authorization bundle and a human-issued approval for
exactly one next iteration. A bundle member is assigned to one logical call
before dispatch, so a five-call adjudication consumes five distinct network
authorities while remaining one bounded iteration. The approval binds the
current canonical state hash, next sequence, grant, bundle, provider and
runner profiles, runner identity/session, and lease fence. Its append-only
consumption occurs before transport construction and is recoverable only at
the same pre-iteration or matching in-flight boundary.

The production-shaped live executor has been exercised with injected
DNS/credential/HTTPS components only. No production network execution is
enabled by the CLI. See `max-research-mr2b2.md` for the complete boundary.
